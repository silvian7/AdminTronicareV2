Decision
Extend the existing Refine/React admin and Python backend. Use the Flutter app as the caregiver experience reference and the daily ingester as the analytical reference.

How to use
Open the existing admin project in Codex. Make the related backend and ingester repositories accessible if they are separate; the Flutter repository is useful but optional. Paste prompts 1 through 6 in order in the same Codex conversation. Let each stage finish and inspect its result before sending the next. Prompt 1 records the actual architecture; prompts 2 through 6 implement and verify it.

The sequence does not assume repository paths, a particular Python framework, a plotting library or a resident data model. Codex must discover those details.

For one continuous run, attach this file and send:
"Read the attached TroniCare caregiver portal prompt file. Execute prompts 1 through 6 in order, treating prompt 1's standing instructions as applicable throughout. Complete each stage's relevant checks before advancing. Make reasonable implementation decisions without repeated confirmations and record progress in the implementation note. Do not execute the optional deployment prompt."

The optional final prompt deploys to the project's established development or staging target. Production deployment is outside that optional prompt.

PROMPT 2
IMPLEMENT THE CAREGIVER API AND SHARED ANALYTICS ACCESS

Extend the existing backend before building screens around assumed endpoints.

BEGIN PROMPT
Continue from the implementation note and inspect the current code before editing. Implement the backend data access required by the caregiver portal in the existing Python application.

Deliver the smallest API surface needed for:
- An authorised subject overview, with search/filtering/pagination where appropriate.
- Available reports and the latest completed report for a subject.
- Report details and summary metrics.
- Time-series measurements and bed-presence intervals for a bounded period.
- Comparable daily metrics for historical trends.

Reuse existing endpoints and schemas where they fit. Add narrowly scoped endpoints only where needed, following existing naming and response conventions.

Data and analytics requirements:
1. Read stored measurements and reports. Opening a page must not execute ingestion, request a full vendor history or regenerate all reports.
2. Reuse the ingester's data preparation and metric definitions. Extract shared functions if necessary, without importing an executable job in a way that starts it or triggers side effects.
3. Preserve existing report values and provenance. Return actual period start/end, timezone, completeness, measurement freshness, report generation time, metric units and available quality information.
4. Keep the report's measurement window separate from the time when the job ran. Honour the actual vendor/local-time convention, including clock changes where applicable.
5. Keep missing measurements, invalid samples, zero movement and out-of-bed states distinct. Return null/unknown where appropriate. Do not claim coverage unless its calculation is defined.
6. For occupancy intervals, establish the valid state at the left boundary from earlier data when possible; otherwise start with unknown. Apply the established freshness rules so old state is not carried indefinitely through missing data.
7. Bound date ranges and response sizes. Aggregate continuous signals when needed while preserving gaps and meaningful extrema. Preserve bed-exit transitions as intervals/events.
8. Keep HRV fields tied to their documented definitions. Do not rename an undefined vendor HRV value as RMSSD. Preserve the actual meaning and calibration of temperature channels.
9. Respect known subject-to-device assignment boundaries. Do not present an entire device history as one resident's history.

Enforce access in the backend for every overview, report, series, trend and download request. Validate organisation membership, the existing subject permissions and parent-child relationships: an allowed subject ID must not make another subject's report ID accessible. Verify caregiver accounts cannot invoke administrative mutations or technical-only endpoints directly, even if the existing admin treated every authenticated user as privileged. Extend the existing authorization model minimally where necessary while preserving authorised administrator access. Use the existing error conventions without leaking protected data.

Add focused tests for allowed access, cross-organisation denial, a mismatched subject/report pair, caregiver denial of an administrative mutation with authorised admin access preserved, time boundaries, missing data and occupancy reconstruction. Use the project's existing test tools.

Make the necessary changes and run relevant backend checks. Prefer existing schema structures; if a migration is genuinely necessary, keep it additive and compatible with existing consumers.

Update the implementation note with the actual API contracts, supported metrics and unresolved limitations. Report changed files, checks actually run and any blocked validation.
END PROMPT
